# Decision Notes — บทบาทที่ 3 (Decision Layer / Backtest)

คู่กับ `modeling_notes.md` ของบทบาทที่ 2 — บันทึกการตัดสินใจของชั้น Overbooking Decision

## 1. สมมติฐานต้นทุน (Cost Assumptions)

### Capacity ต่อโรงแรม
- **วิธีประมาณ:** percentile ที่ 95 (p95) ของจำนวนการจองพร้อมกันต่อคืน (นับจาก arrival_date) จากข้อมูล train
  (คำนวณด้วย `overbooking_decision/suggest_capacity.py --train-csv data/processed/train.csv`)
- **ค่าที่ใช้จริง:** City Hotel = **190 ห้อง**, Resort Hotel = **91 ห้อง**
- **เหตุผลที่เลือก p95 แทน max:** ป้องกันไม่ให้ capacity ถูกดึงสูงเกินจริงโดย outlier วันเดียว
  (เช่นเทศกาลพิเศษที่ไม่ใช่ภาวะปกติของโรงแรม)
- **ข้อสังเกตสำคัญที่พบระหว่างทดสอบ:** ค่า capacity นี้สูงกว่าจำนวนการจองเฉลี่ยต่อคืนในชุด test/production
  มาก (~71 การจอง/คืน/โรงแรม เทียบ capacity 190/91) ดูหัวข้อ 6 สำหรับคำอธิบายและข้อจำกัดที่เกี่ยวข้อง

### ต้นทุนห้องว่าง (cost_empty)
= adr เฉลี่ยของคืนนั้น (รายได้ที่เสียไปเมื่อห้องว่างโดยไม่มีใครเข้าพัก)

### ต้นทุนจองเกิน (cost_overbook = k × adr)
ทดสอบ k = 1.5, 2.0, 3.0 (ค่าเริ่มต้นที่ใช้รายงานหลักคือ **k = 2.0**)

**เหตุผลเลือกช่วง k นี้:** ค่าชดเชยลูกค้าที่ถูกปฏิเสธจริง ๆ มักรวมทั้งค่าห้องโรงแรมทดแทน (มักแพงกว่าราคาที่จองไว้)
บวกค่าเดินทาง/ค่าชดเชยความไม่สะดวก และความเสียหายต่อชื่อเสียง (goodwill) จึงสมเหตุสมผลที่จะสูงกว่าราคาห้อง 1.5–3 เท่า
ไม่มีตัวเลขจริงในชุดข้อมูล จึงต้องทำ sensitivity เพื่อตอบคำถามว่า "ถ้าสมมติฐานนี้ผิดไปเท่าไหร่ ข้อสรุปยังเหมือนเดิมไหม"

## 2. การเรียงลำดับการจอง (Booking Priority Assumption)

เรียงตาม `lead_time` จากมากไปน้อย (สมมติว่าจองล่วงหน้านานกว่า = จองเข้ามาก่อน = ควรได้สิทธิ์รับก่อนแบบ FCFS)

**ข้อจำกัด:** ชุดข้อมูลไม่มีคอลัมน์วันที่จองจริง (booking_date) จึงใช้ `lead_time` เป็นตัวแทน — ถ้าทีมมีข้อมูลนี้จริงในภายหลัง ควรเปลี่ยนไปเรียงตาม booking_date แทนเพื่อความแม่นยำกว่า

## 3. วิธีการของ Decision Layer

1. รับความน่าจะเป็นยกเลิกที่ calibrate แล้วจากบทบาทที่ 2 (`models:/hotel-cancellation-classifier@candidate`,
   Random Forest max_depth=8/min_samples_leaf=50 + isotonic calibration, ECE 0.0379)
2. Monte Carlo simulation (n_sims = 2000, seed = 42) จำลองว่าการจองแต่ละรายการ "มาจริง" หรือไม่ (Bernoulli ตาม 1 − p_cancel)
3. ไล่ค่า o (จำนวนห้องที่รับจองเกิน) ตั้งแต่ 0 ถึง 30% ของ capacity หาค่าที่ต้นทุนคาดหวังต่ำสุด
   (ต้นทุนคาดหวัง = ห้องว่าง × cost_empty + ลูกค้าที่ต้องย้าย × cost_overbook)
4. Backtest เปรียบเทียบกับอีก 3 นโยบาย (ไม่ overbook / คงที่ 5% / ตามอัตรายกเลิกเฉลี่ยรายเดือน) บน**ผลจริง** (ไม่ใช่การจำลอง) ของคืนในชุด test และ production

## 4. ผลการ Backtest (4 นโยบาย, k = 2.0)

### บน test set (`data/processed/test.csv` — 12,789 การจอง, 90 วัน × 2 โรงแรม = 180 คืน)

| นโยบาย | กำไรรวม | ลูกค้าที่ถูกย้าย | ลูกค้าที่ถูกย้าย/1,000 คืน |
|---|---:|---:|---:|
| avg_rate | −444,212 | 16 | 88.9 |
| **model** | **−460,302** | **2** | **11.1** |
| fixed | −541,294 | 0 | 0.0 |
| no_overbook | −570,063 | 0 | 0.0 |

### บน production (`data/processed/production.csv` — 27,830 การจอง, 153 วัน × 2 โรงแรม = 306 คืน)

| นโยบาย | กำไรรวม | ลูกค้าที่ถูกย้าย | ลูกค้าที่ถูกย้าย/1,000 คืน |
|---|---:|---:|---:|
| avg_rate | −1,831,823 | 35 | 114.4 |
| **model** | **−1,968,286** | **19** | **62.1** |
| fixed | −2,316,575 | 0 | 0.0 |
| no_overbook | −2,418,945 | 0 | 0.0 |

**สรุป:** นโยบาย **model** ให้กำไรสูงกว่า no_overbook **+19.3%** (test) / **+18.6%** (production) และสูงกว่า fixed
**+15.0%** (test) / **+15.0%** (production) อย่างสม่ำเสมอทั้งสองชุดข้อมูล

**แต่** model แพ้ avg_rate ด้านกำไร (**−3.6%** ที่ test, **−7.4%** ที่ production) — สิ่งที่ทำให้แตกต่างจาก
avg_rate คือ model **ระมัดระวังกว่ามาก** ในการ overbook: ลูกค้าที่ถูกย้ายน้อยกว่า avg_rate ถึง 8 เท่าที่ test
(2 vs 16 คน) และเกือบ 2 เท่าที่ production (19 vs 35 คน) เพราะ cost_overbook = k×adr ทำให้การย้ายลูกค้า 1 คน
"แพง" กว่าห้องว่าง 1 ห้อง (k=2) โมเดลจึงยอมเสียกำไรจุดเล็กน้อยเพื่อลดความเสี่ยงด้านประสบการณ์ลูกค้าลงมาก —
เป็น **trade-off ที่อธิบายได้และเป็นจุดขายของ decision layer** ไม่ใช่ข้อบกพร่อง ควรนำเสนอเป็นเรื่องเล่าหลักตอน
พูดถึง "กำไรเทียบ baseline" ในสไลด์

## 5. Sensitivity Analysis (ค่า k = 1.5 / 2.0 / 3.0)

### กำไรรวม — test set

| นโยบาย | k=1.5 | k=2.0 | k=3.0 |
|---|---:|---:|---:|
| avg_rate | −443,480 | −444,212 | −445,677 |
| model | −460,214 | −460,302 | −460,478 |
| fixed | −541,294 | −541,294 | −541,294 |
| no_overbook | −570,063 | −570,063 | −570,063 |

### กำไรรวม — production

| นโยบาย | k=1.5 | k=2.0 | k=3.0 |
|---|---:|---:|---:|
| avg_rate | −1,829,695 | −1,831,823 | −1,836,080 |
| model | −1,967,113 | −1,968,286 | −1,970,630 |
| fixed | −2,316,575 | −2,316,575 | −2,316,575 |
| no_overbook | −2,418,945 | −2,418,945 | −2,418,945 |

**สรุป robustness:** อันดับกำไร (avg_rate > model > fixed > no_overbook) **คงที่ทุกค่า k** ทั้งใน test และ
production — ข้อสรุปเรื่อง "model ดีกว่า baseline แบบ static แต่แพ้ avg_rate เรื่องกำไร" จึงไม่ได้ขึ้นอยู่กับ
สมมติฐานค่า k ที่ตั้งไว้แคบ ๆ ค่าเดียว

**สิ่งที่สังเกตเห็นเพิ่มเติม (สำคัญ):** จำนวนลูกค้าที่ถูกย้ายของนโยบาย model **ไม่เปลี่ยนเลย** ไม่ว่า k จะเป็น
เท่าไหร่ (คงที่ 2 คนที่ test, 19 คนที่ production ทุกค่า k) ทั้งที่ทฤษฎีคาดว่า k สูงขึ้นควรทำให้โมเดล overbook
น้อยลง สาเหตุคือ **capacity (190/91) สูงกว่าจำนวนการจองเฉลี่ยต่อคืนมาก** (~71 การจอง/คืน/โรงแรม) ห้องจึง
แทบไม่เคยเต็มไม่ว่าจะตั้งค่า o เท่าไหร่ในช่วงที่ค้นหา ทำให้ต้นทุนแทบไม่ขึ้นกับ o หรือ k เลยในทางปฏิบัติ — ดูข้อจำกัด
ข้อสุดท้ายในหัวข้อ 6 ที่อาจเป็นสาเหตุราก

## 6. ข้อจำกัด (ต้องเขียนในรายงานหลักด้วย)

- **กำไรเป็นการจำลองบนข้อมูลอดีต:** ไม่รู้ว่าลูกค้าที่ถูกปฏิเสธการจองจริง ๆ จะพยายามจองที่อื่นหรือหายไปเลย ตัวเลขกำไรจึงเป็นค่าประมาณภายใต้สมมติฐานว่าพฤติกรรมไม่เปลี่ยนจากอดีต
- **ต้นทุนเป็นค่าที่ตั้งเอง:** ชุดข้อมูลไม่มี capacity และค่าชดเชยจริง ได้ทำ sensitivity ของ k เพื่อลดความเสี่ยงจากสมมติฐานนี้
- **การเรียงลำดับการจองใช้ lead_time แทน booking_date จริง** (ดูหัวข้อ 2)
- **Concept drift ที่เกิดเองในข้อมูลมีจำกัด:** ครอบคลุมช่วงเวลาสั้นและสองโรงแรมเท่านั้น จึงอาจไม่สะท้อนสถานการณ์เปลี่ยนนโยบายเงินมัดจำในโลกจริงได้ครบถ้วน
- **การนับ capacity/occupancy ต่อคืนนับเฉพาะ arrival_date ไม่นับการพักต่อเนื่อง:** ชุดข้อมูลไม่มีคอลัมน์ occupancy
  ต่อคืนโดยตรง โค้ดปัจจุบันนับ "จำนวนการจองต่อคืน" จากวันที่เช็กอิน (arrival_date) เท่านั้น **ไม่ได้นับรวมแขกที่
  เช็กอินมาก่อนแล้วยังพักอยู่ต่อ** (multi-night stay ที่ครอบคลุมคืนนั้นด้วย) ทำให้ทั้งค่า capacity ที่ประมาณไว้และ
  จำนวนผู้เข้าพักจริงที่ใช้ backtest อาจต่ำกว่าความเป็นจริง — สังเกตได้จากผลใน sensitivity ที่ o_star แทบไม่ขยับ
  ตามค่า k เลย (เพราะ demand ที่นับได้ต่ำกว่า capacity มากจนห้องแทบไม่เคยเต็ม) ถ้ามีเวลาควรปรับให้นับ occupancy
  จริงจาก stays_in_weekend_nights + stays_in_week_nights แทน แล้ว rerun suggest_capacity.py และ backtest ใหม่
