# Decision Notes — บทบาทที่ 3 (Decision Layer / Backtest)

คู่กับ `modeling_notes.md` ของบทบาทที่ 2 — บันทึกการตัดสินใจของชั้น Overbooking Decision

> **อัปเดต v2:** ผลทั้งหมดในไฟล์นี้มาจาก backtest แบบ sequential (`backtest_sequential.py`) ซึ่งนับแขกที่พักต่อเนื่องหลายคืนแล้ว
> ผลดิบอยู่ใน `overbooking_decision_result/` ผลรุ่นแรก (นับเฉพาะวันเช็กอิน) ถูกแทนที่ทั้งหมด เหตุผลของการเปลี่ยนอยู่ในหัวข้อ 6

## 1. สมมติฐานต้นทุน (Cost Assumptions)

ค่าทั้งหมดอยู่ใน `overbooking_decision/config.yaml` ที่เดียว

### Capacity ต่อโรงแรม
- **วิธีประมาณ:** percentile ที่ 95 (p95) ของ occupancy จริงต่อคืนจากข้อมูล train
  นับรวมแขกที่เช็กอินมาก่อนแล้วยังพักอยู่ (`compute_nightly_occupancy()` ใน `real_data_adapter.py`)
  คำนวณด้วย `overbooking_decision/suggest_capacity.py --train-csv data/processed/train.csv`
- **ค่าที่ใช้:** City Hotel = **190 ห้อง**, Resort Hotel = **91 ห้อง**
- **เหตุผลที่เลือก p95 แทน max:** ป้องกันไม่ให้ capacity สูงเกินจริงเพราะ outlier วันเดียว เช่น เทศกาลพิเศษ

### ต้นทุนห้องว่าง (cost_empty)
= adr ของคืนนั้น (รายได้ที่เสียไปเมื่อห้องว่าง)

### ต้นทุนจองเกิน (cost_overbook = k × adr)
ทดสอบ k = 1.5, 2.0, 3.0 (ค่าหลักที่ใช้รายงานคือ **k = 2.0**)

**เหตุผลเลือกช่วง k นี้:** ค่าชดเชยลูกค้าที่ถูกย้ายมักรวมค่าห้องโรงแรมทดแทน (มักแพงกว่าราคาที่จองไว้)
ค่าเดินทาง ค่าชดเชยความไม่สะดวก และความเสียหายต่อชื่อเสียง จึงสมเหตุสมผลที่จะสูงกว่าราคาห้อง 1.5–3 เท่า
ชุดข้อมูลไม่มีตัวเลขจริง จึงทำ sensitivity เพื่อดูว่าข้อสรุปเปลี่ยนไหมถ้าสมมติฐานนี้คลาดเคลื่อน

## 2. การเรียงลำดับการจอง (Booking Priority Assumption)

เรียงตาม `lead_time` จากมากไปน้อย (สมมติว่าจองล่วงหน้านานกว่า = จองเข้ามาก่อน = ได้สิทธิ์รับก่อนแบบ FCFS)

**ข้อจำกัด:** ชุดข้อมูลไม่มีวันที่จองจริง (booking_date) จึงใช้ `lead_time` เป็นตัวแทน

## 3. วิธีการของ Decision Layer

1. รับความน่าจะเป็นยกเลิกที่ calibrate แล้วจากบทบาทที่ 2 (`models:/hotel-cancellation-classifier@candidate`,
   Random Forest max_depth=8 / min_samples_leaf=50 + isotonic calibration, ECE 0.0379)
2. Monte Carlo (n_sims = 2,000, seed = 42) จำลองว่าการจองแต่ละรายการมาจริงหรือไม่ (Bernoulli ตาม 1 − p_cancel)
3. หัก carryover (ห้องที่แขกจากคืนก่อนยังพักอยู่และไม่ได้ยกเลิก) ออกจาก capacity ได้ effective_capacity
4. ไล่ค่า o (จำนวนห้องที่รับจองเกิน) ตั้งแต่ 0 ถึง 30% ของ capacity หาค่าที่ต้นทุนคาดหวังต่ำสุด
   (ต้นทุนคาดหวัง = ห้องว่าง × cost_empty + ลูกค้าที่ต้องย้าย × cost_overbook)
5. Backtest เทียบกับอีก 3 นโยบายบน**ผลจริง** (ไม่ใช่การจำลอง) ของทุกคืนในชุด test และ production
   โดยเดินทีละคืนและส่ง carryover ต่อไปคืนถัดไป (`backtest_sequential.py`)

| นโยบาย | วิธีกำหนด o | ใช้ capacity แบบไหน |
|---|---|---|
| no_overbook | o = 0 | effective_capacity |
| fixed | 5% ของ capacity เต็ม | capacity เต็ม (ไม่หัก carryover) |
| avg_rate | capacity เต็ม × อัตรายกเลิกเฉลี่ยรายเดือนของโรงแรมนั้น | capacity เต็ม (ไม่หัก carryover) |
| **model** | o ที่ต้นทุนคาดหวังต่ำสุดจาก Monte Carlo | effective_capacity |

## 4. ผลการ Backtest (4 นโยบาย, k = 2.0)

ผลดิบ: `overbooking_decision_result/real_backtest_summary.csv` (test) และ `prod_sim_backtest_summary.csv` (production)

### บน test set (`data/processed/test.csv` — 12,789 การจอง, 204 คืน-โรงแรม)

| นโยบาย | กำไรรวม | เทียบไม่รับเกิน | ลูกค้าที่ถูกย้าย | ย้าย/1,000 คืน |

### บน production (`data/processed/production.csv` — 27,830 การจอง, 329 คืน-โรงแรม)

| นโยบาย | กำไรรวม | เทียบไม่รับเกิน | ลูกค้าที่ถูกย้าย | ย้าย/1,000 คืน |
|---|---:|---:|---:|---:|
| avg_rate | 4,031,032 | +36.9% | 6,521 | 19,821 |
| **model** | **3,767,922** | **+27.9%** | **27** | **82** |
| fixed | 3,436,208 | +16.7% | 33 | 100 |
| no_overbook | 2,945,321 | — | 0 | 0 |

**สรุป**
- model ได้กำไรมากกว่า no_overbook **+25.3%** (test) / **+27.9%** (production)
  และมากกว่า fixed **+10.6%** (test) / **+9.7%** (production) โดยย้ายลูกค้า**น้อยกว่า** fixed ด้วย
- avg_rate ได้กำไรมากกว่า model **12.1%** (test) / **7.0%** (production)
  แต่ย้ายลูกค้ามากกว่า **44 เท่า** (1,502 vs 34) และ **241 เท่า** (6,521 vs 27)
  เฉลี่ยเกือบ 20 คนต่อคืนบน production ซึ่งใช้จริงไม่ได้
- สาเหตุที่ avg_rate ย้ายลูกค้ามาก: สูตรใช้ capacity เต็มโดยไม่หักห้องที่แขกจากคืนก่อนยังพักอยู่
  จึงรับเกินซ้อนทุกคืน ส่วน model ตัดสินใจจากห้องที่เหลือจริงและรับเกินเฉพาะคืนที่คุ้มความเสี่ยง

## 5. Sensitivity Analysis (k = 1.5 / 2.0 / 3.0)

ผลดิบ: `overbooking_decision_result/real_sensitivity.csv`, `prod_sim_sensitivity.csv` และกราฟ `*_sensitivity_plot.png`

### กำไรรวม (ลูกค้าที่ถูกย้าย) — test set

| นโยบาย | k = 1.5 | k = 2.0 | k = 3.0 |
|---|---:|---:|---:|
| avg_rate | 1,166,669 (1,502) | 1,113,504 (1,502) | 1,007,173 (1,502) |
| **model** | **993,375 (35)** | **993,129 (34)** | **989,422 (27)** |
| fixed | 900,089 (70) | 898,073 (70) | 894,041 (70) |
| no_overbook | 792,663 (0) | 792,663 (0) | 792,663 (0) |

### กำไรรวม (ลูกค้าที่ถูกย้าย) — production

| นโยบาย | k = 1.5 | k = 2.0 | k = 3.0 |
|---|---:|---:|---:|
| avg_rate | 4,491,372 (6,521) | 4,031,032 (6,521) | 3,110,350 (6,521) |
| **model** | **3,780,738 (29)** | **3,767,922 (27)** | **3,761,027 (26)** |
| fixed | 3,437,919 (33) | 3,436,208 (33) | 3,432,784 (33) |
| no_overbook | 2,945,321 (0) | 2,945,321 (0) | 2,945,321 (0) |

**สรุป**
- **model ชนะ fixed และ no_overbook ทุกค่า k** ทั้ง test และ production
- **อันดับระหว่าง model กับ avg_rate ขึ้นกับ k:** ที่ k = 3.0 บน production model ได้กำไรมากกว่า avg_rate
  (3,761,027 vs 3,110,350) เพราะ avg_rate ย้ายลูกค้าจำนวนเท่าเดิมทุกค่า k จึงเสียค่าชดเชยหนักขึ้นตาม k
  บน test avg_rate ยังกำไรสูงกว่าเล็กน้อยที่ k = 3.0 (1,007,173 vs 989,422)
- **กำไรของ model แทบไม่เปลี่ยนตาม k** (ต่างกันไม่ถึง 0.6%) เพราะ model ปรับจำนวนรับเกินลงเองเมื่อการย้ายลูกค้าแพงขึ้น
  ลูกค้าที่ถูกย้ายลดลงจาก 35 → 34 → 27 (test) และ 29 → 27 → 26 (production)
  ยืนยันว่าการแก้ capacity ในหัวข้อ 6 ได้ผล (รุ่นแรกจำนวนลูกค้าที่ย้ายไม่ขยับตาม k เลย)

## 6. ข้อจำกัดและการเปลี่ยนแปลงจากรุ่นแรก

### สิ่งที่แก้ใน v2
รุ่นแรก (`backtest.py`) นับ occupancy ต่อคืนจาก arrival_date อย่างเดียว ไม่นับแขกที่พักต่อเนื่องหลายคืน
ห้องจึงแทบไม่เคยเต็ม และ o* ไม่ตอบสนองต่อค่า k v2 แก้ 2 จุด

- `compute_nightly_occupancy()` นับ occupancy จริงจาก stays_in_weekend_nights + stays_in_week_nights
  ใช้ทั้งประมาณ capacity และ backtest
- `backtest_sequential.py` เดินทีละคืน เก็บการจองที่ยังพักอยู่เป็น state แล้วหัก carryover ก่อนตัดสินใจรับจองใหม่

ผลรุ่นแรกยังรันได้ด้วย `run_real_backtest.py --naive` สำหรับเทียบ

### ข้อจำกัดที่ยังเหลือ
- **กำไรเป็นการจำลองบนข้อมูลอดีต:** ไม่รู้ว่าลูกค้าที่ถูกปฏิเสธจะจองที่อื่นหรือหายไป
- **ต้นทุนเป็นค่าที่ตั้งเอง:** ชุดข้อมูลไม่มี capacity และค่าชดเชยจริง จึงทำ sensitivity ของ k
  ต้นทุน k × adr ยังไม่รวมผลระยะยาว เช่น รีวิวเสียหรือลูกค้าไม่กลับมา ต้นทุนจริงของนโยบายที่ย้ายลูกค้ามากจึงสูงกว่าที่เห็น
- **avg_rate ได้เปรียบในการทดสอบ:** อัตรายกเลิกเฉลี่ยรายเดือนคำนวณจากชุดที่ใช้ทดสอบเอง (`run_real_backtest.py`)
  เท่ากับรู้อัตรายกเลิกจริงของเดือนนั้นล่วงหน้า ในการใช้งานจริงต้องใช้อัตราจากอดีต ผลของ avg_rate จึงดีเกินจริง
- **carryover ที่ต้นไฟล์ถูกนับต่ำไปเล็กน้อย:** การจองที่เริ่มพักก่อนช่วงของไฟล์ test/production ไม่ได้ถูกนับ
- **การเรียงลำดับการจองใช้ lead_time แทน booking_date จริง** (หัวข้อ 2)
- **carryover ใช้ is_canceled จริง:** สมมติว่าโรงแรมรู้ผลของการจองที่รับไปแล้ว ณ คืนที่ตัดสินใจ
