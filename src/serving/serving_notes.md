## 1. โครงสร้าง API

| Endpoint | หน้าที่ |
| --- | --- |
| `GET /health` | เช็กว่า API ทำงานและโหลดโมเดลได้ (`ok` หรือ `model_not_loaded`) |
| `GET /metrics` | จำนวน request, error rate และ latency p50/p95 ต่อ endpoint เทียบกับ SLO |
| `POST /predict` | ทำนาย 1 การจอง (endpoint หลัก ใช้ตอนรับจองแบบ real-time และใช้รับ test case ของอาจารย์) |

### ใช้ build_features() ตัวเดียวกับตอนเทรน

API แปลงข้อมูลที่รับเข้าด้วย `build_features()` ของบทบาทที่ 2 เสมอ ไม่เขียนการแปลงข้อมูลซ้ำเอง เพื่อกัน Training-Serving Skew

`build_features()` ต้องการคอลัมน์ครบเหมือนข้อมูลตอนเทรน (รวมคอลัมน์ที่มันตัดทิ้งเอง เช่น `is_canceled`, `reservation_status`, `row_id`) API จึงอ่านชื่อคอลัมน์จากหัวตารางของ `data/processed/test.csv` แล้วเติมคอลัมน์ที่ผู้ใช้ไม่ได้ส่งเป็นค่าว่าง ทั้ง 8 คอลัมน์ที่ถูกเติมเป็น target, leakage หรือคอลัมน์ช่วย ไม่มีตัวไหนเป็น feature ที่โมเดลใช้จริง

**หลักฐาน:** เทส `test_batch_matches_single_predict` ยืนยันว่า `/predict` และ `/predict-batch` ให้ความน่าจะเป็นเท่ากันทุกหลัก และผลใน Docker (`p_cancel = 0.6886`) ตรงกับผลบนเครื่องพัฒนาทุกหลัก

### ตรวจข้อมูลก่อนเข้าโมเดล (ตอบ 422)

ใช้ Pydantic กำหนดรูปแบบข้อมูล (`src/serving/schemas.py`) ข้อมูลผิดจะไม่ถูกส่งเข้าโมเดลเลย และได้ข้อความที่บอกว่าช่องไหนผิด กรณีที่จับได้:

* `lead_time`, `adr`, จำนวนผู้เข้าพัก ติดลบ
* ผู้เข้าพักเป็นศูนย์ทั้งหมด (adults + children + babies = 0)
* เดือนสะกดผิด, ชื่อโรงแรมหรือ `deposit_type` ไม่อยู่ในค่าที่อนุญาต
* ขาดช่องที่บังคับ, ส่งรายการว่างใน batch, มีรายการผิดปนใน batch (บอก index ของรายการที่ผิด)

### /recommend-overbooking

* **บังคับส่ง** `already_occupied` (ไม่มีค่าเริ่มต้น) ตามที่บทบาทที่ 3 เตือนว่าถ้าปล่อยเป็น 0 ระบบจะเข้าใจว่าห้องว่างทั้งหมดแล้วแนะนำ overbook เกินจริง และตอบ 422 ถ้าค่าเกินจำนวนห้องของโรงแรม
* เรียงการจองจาก `lead_time` มากไปน้อยก่อนส่งเข้า decision layer ตามสมมติฐาน FCFS ของบทบาทที่ 3
* ถ้าไม่ส่ง `adr_ref` ใช้ adr เฉลี่ยของการจองใหม่
* การจองทุกรายการต้องเป็นโรงแรมเดียวกับที่ขอคำแนะนำ
* โหลด `config.yaml` ครั้งเดียวตอนเปิด API ไม่อ่านไฟล์ใหม่ทุก request

**ตัวอย่างผลจริง:** City Hotel เหลือห้องว่าง 1 ห้อง มีการจองใหม่ 2 รายการ (ความน่าจะเป็นยกเลิกเฉลี่ย 41%, คาดว่ามาจริง 1.2 คน) ได้ `o_star = 1` คือรับทั้งสองรายการ

## 2. วิธีวัด

### สภาพแวดล้อม

* Laptop 20 logical threads, Windows + Docker Desktop (WSL2, RAM ให้ Docker 7.5 GB), Python 3.13
* Locust 2.46.6 รันบนเครื่องเดียวกับ API (แย่ง CPU กัน ตัวเลขจึงต่ำกว่าเซิร์ฟเวอร์แยก)
* ปิด container อื่นที่ไม่เกี่ยวข้องก่อนวัดใน Docker

### การทดสอบ 2 แบบ

| แบบ | ไฟล์ | ใช้ตอบคำถาม |
| --- | --- | --- |
| ความจุสูงสุด | `load_test/locustfile.py` | 20 ผู้ใช้ยิงต่อเนื่องไม่พัก (ข้อมูลถูก 10 : ผิด 1) → throughput สูงสุดเท่าไร |
| SLO อัตราคงที่ | `load_test/locustfile_slo.py` | ผู้ใช้ละ 2 req/s (60 ผู้ใช้ = 120 req/s) → ที่โหลดนี้ p95 เท่าไร |

**เหตุผลที่แยก:** การยิงเต็มกำลังสร้างคิวยาวโดยตั้งใจ latency ที่ได้จึงเท่ากับ จำนวนผู้ใช้ ÷ throughput เสมอ (เช่น 20 ÷ 166 ≈ 120 ms) เหมาะกับการหาความจุ แต่ไม่ใช่วิธีวัด p95 ตาม SLO

ใน Docker ยิงจาก container Locust ที่อยู่ในเครือข่ายเดียวกับ API (`--network container:hotel-api`) เพื่อตัด overhead ของการส่งต่อ port ระหว่าง Windows กับ Docker ออก

## 4. ปัญหาที่พบและวิธีแก้

### 4.1 โมเดลใช้ทุก core ทั้งที่ทำนายแค่แถวเดียว

**อาการ:** request ที่ได้ 422 (ไม่เรียกโมเดล) ใช้เวลา 5 ms แต่ `/predict` ใช้อย่างน้อย 148 ms

**สาเหตุ:** Random Forest เทรนด้วย `n_jobs=-1` ตอนทำนายแถวเดียวจึงแบ่งต้นไม้ 300 ต้นให้ 20 thread แล้วรอรวมผล เวลาที่เสียกับการแบ่งงานมากกว่าตัวงานจริง

**วิธีแก้:** ครอบการทำนายด้วย `parallel_config(backend="sequential")` ไม่ต้องเทรนใหม่ ผลทำนายเหมือนเดิมทุกหลัก เวลาลดจาก 39.1 เหลือ 18.7 ms

### 4.2 ช้าเพิ่ม 45 ms ทุก request เมื่อรันหลาย worker บน Linux

**อาการ:** ใน Docker request ที่ได้ 422 ช้าคงที่ 50 ms แม้มีผู้ใช้คนเดียว แต่ API วัดเวลาตัวเองได้แค่ ~30 ms สำหรับ `/predict`

**การพิสูจน์:** รัน 1 worker แล้ว 422 เหลือ 1 ms ทันที จึงรู้ว่าเกิดเฉพาะโหมดหลาย worker

**สาเหตุ:** Python เปิด TCP_NODELAY ให้เฉพาะ socket ที่ระบุว่าเป็น TCP แต่ uvicorn แบบ `--workers` สร้าง socket กลางโดยไม่ระบุ ทุก worker จึงไม่ได้เปิด เมื่อ FastAPI ส่งคำตอบเป็น 2 ท่อน ท่อนที่สองต้องรอ Linux ตอบรับท่อนแรกซึ่งหน่วงไว้ 40 ms บน Windows ไม่เจอ

**วิธีแก้:** ตั้งให้เปิด TCP_NODELAY กับ TCP socket ทุกตัวใน `app.py` ผล: 422 จาก 50 เหลือ 2 ms, throughput จาก 132 เป็น 158 req/s

### 4.3 worker แย่ง GIL กันเมื่อมีงานพร้อมกันเยอะ

**อาการ:** เพิ่มผู้ใช้จาก 20 เป็น 60 แต่ throughput ลดลงจาก 144 เหลือ 95 req/s

**สาเหตุ:** endpoint แบบ `def` ถูกรันใน thread pool worker ละหลาย thread พร้อมกัน แต่ Python คำนวณได้ทีละ thread เพราะ GIL จึงเสียเวลาสลับไปมา

**วิธีแก้:** เปลี่ยน endpoint ที่เรียกโมเดลเป็น `async def` ให้แต่ละ worker ทำทีละงานตามลำดับ p50 ที่ 120 req/s ลดจาก 600 เหลือ 280 ms

### 4.4 งานกระจายไม่เท่ากันระหว่าง worker

**อาการ:** ที่ 80 req/s (ครึ่งเดียวของความจุ) เปอร์เซ็นไทล์แยกเป็นสองกลุ่ม p50 = 150 ms แต่ p66 กระโดดเป็น 500 ms

**สาเหตุ:** ผู้ใช้จำลองแต่ละคนเปิดการเชื่อมต่อค้างไว้ (keep-alive) และติดอยู่กับ worker ตัวเดิม บาง worker รับผู้ใช้ไปมากจนคิวยาว ขณะที่ตัวอื่นว่าง

**วิธีแก้:** SLO test ส่ง `Connection: close` ปิดการเชื่อมต่อหลังทุก request ซึ่งตรงกับการใช้งานจริงที่การจองแต่ละรายการมาจากลูกค้าคนละราย ผล: รับ 120 req/s ได้ครบ และ p95 ลดจาก 730 เหลือ 330 ms

## 5. SLO ที่ประกาศ

| SLO | ค่าเสนอในสโคป | ตกลงรอบแรก (วัดบน Windows) | **ประกาศสุดท้าย (วัดใน Docker)** | วัดได้ |
| --- | --- | --- | --- | --- |
| Throughput ต่อ container | ≥ 200 req/s | ≥ 150 req/s | **≥ 150 req/s** | 158 req/s ✓ |
| p95 ของ /predict | ≤ 100 ms | ≤ 100 ms ที่ 120 req/s | **≤ 350 ms ที่ 120 req/s** | 330 ms ✓ |
| Error rate (5xx) | ≤ 1% | ≤ 1% | **≤ 1%** | 0% ✓ |

**เหตุผลที่ปรับ:** สโคประบุว่าตัวเลข threshold ทั้งหมดเป็นค่าเสนอ ต้องวัดจริงก่อนประกาศ หลังแก้ปัญหาฝั่ง API ครบแล้ว (หัวข้อ 4) ที่เหลือคือเวลาคำนวณของโมเดลเองกับ CPU ของ laptop ที่แบ่งให้ 8 workers, Locust และ Docker

**หลักฐานว่า p95 ไม่ได้มาจากปริมาณงาน:** ลดโหลดจาก 120 เหลือ 60 req/s แล้ว p95 แทบไม่ลด (260–340 ms) และยิงซ้ำเงื่อนไขเดียวกันได้ผลต่างกันเกือบเท่าตัว หางช้าจึงมาจากความไม่นิ่งของเครื่อง ไม่ใช่จาก API ทีมจึงเลือกประกาศตามที่วัดได้จริง แทนการคงเป้า 100 ms ที่จะทำให้ alert ของบทบาทที่ 6 ดังตลอดเวลา

**ทางเลือกที่ยังเปิดไว้:** ถ้าบทบาทที่ 2 ลดต้นไม้จาก 300 เหลือ ~100 แล้ว ECE/PR-AUC ยังผ่าน gate จะลดเวลาส่วนที่ใหญ่ที่สุด (52%) และวัดใหม่ได้

## 6. Docker และการใช้โมเดลใน container

`mlflow.db` จดที่อยู่ไฟล์โมเดลเป็น path เต็มของเครื่องที่เทรน (`C:\Users\...\mlruns`) เมื่อเปิดใน container (Linux) จะขึ้น `No such artifact` จึงเขียน `src/serving/export_model.py` คัดลอกโมเดลของ alias ที่ต้องการออกมาเป็นโฟลเดอร์ `serving_model/` แล้วให้ container โหลดจากโฟลเดอร์นั้น (ตั้งผ่าน `MODEL_DIR`)

```powershell
python -m src.serving.export_model
docker build -t hotel-api .
docker run -d --rm -p 8000:8000 -v "${PWD}\serving_model:/app/serving_model:ro" -v "${PWD}\data\processed:/app/data/processed:ro" --name hotel-api hotel-api
```

รายละเอียดสำหรับบทบาทที่ 5 (ตัวอย่าง docker-compose, healthcheck, ลำดับรันใน DAG, การ rollback) อยู่ใน `src/serving/HANDOFF_TO_ROLE5.md`

## 8. ข้อจำกัด (ต้องเขียนในรายงานหลักด้วย)

* **ตัวเลข SLO วัดบน laptop** ที่รัน Locust และ Docker ร่วมกัน p95 แกว่งตามภาระของเครื่อง บนเซิร์ฟเวอร์แยกควรวัดใหม่
* `/metrics` **นับแยกต่อ worker** ถ้ารัน 8 worker จะเห็นแค่ของ worker ที่ตอบ request นั้น ภาพรวมต้องใช้ Locust หรือ Prometheus
* `already_occupied` **ต้องมาจากระบบจองของโรงแรม** เวอร์ชันนี้ผู้เรียกต้องส่งค่าเอง API ไม่ได้คำนวณให้
* **API อ่านโมเดลครั้งเดียวตอนเริ่ม** การ promote/rollback ต้อง export ใหม่แล้วรีสตาร์ท container
* **SLO test สมมติว่าทุก request มาจากลูกค้าคนละราย** (ปิดการเชื่อมต่อทุกครั้ง) ถ้ามีระบบภายนอกที่ต่อสายค้างไว้ยิงถี่ๆ งานอาจกระจายไม่เท่ากันระหว่าง worker
* **การแก้ TCP_NODELAY เป็นการแก้ในระดับ Python** ถ้าอัปเกรด uvicorn หรือ Python ในอนาคตควรวัดซ้ำว่ายังจำเป็นหรือไม่
